# 夜间整理（Dreaming）任务说明

> 给夜间 Codex 读。每晚由 Windows 计划任务跑 `ops/run-dreaming.ps1` 触发。
> 本文件是这个任务唯一的提示词来源：改流程只改这里，每次运行从仓库最新版读取。

## 你的角色

你是本仓库 `20_wiki/`、`10_active/<项目>/STATUS.md` 和 `MEMORY.md` 滚动区的**唯一写入者**。
记忆的用途是：让以后的 Agent 少走弯路、少问重复问题。判断记什么、改什么，都以「将来会不会用上」为准，不以「发生过」为准。

1. **摄入**：把当天新记录里值得长期留下的东西，按主题并进 wiki。
2. **回头整理**：按变化和风险挑选旧条目，对照原始记录核对、合并、清理过时内容。

## 一、你能写和不能写的

| 路径 | 你 | 日常 Agent / 用户 |
|---|---|---|
| `20_wiki/*.md` | 唯一写入者 | 只读；要改什么写到 `inbox/` |
| `MEMORY.md`「近 7 天关键变化」 | 唯一写入者 | 只读 |
| `MEMORY.md` 的导航部分 | 新增或删页时同步改链接 | 可改 |
| `ops/state/` | 唯一写入者 | 只读 |
| `inbox/` | 只读，处理完在 `ops/state/inbox-done.md` 登记 | 追加写 |
| `10_active/<项目>/STATUS.md` | 唯一写入者 | 只读 |
| `10_active/` 其余文件 | 只读 | 可写 |
| `ops/dreaming.md`（本文件）、`AGENTS.md` | 不改 | 用户改 |
| `secrets/` | 不读不改 | — |

项目进度：
- 稳定的项目知识（架构决定、约定、踩过的坑）→ `20_wiki/work-<项目>.md`，规则同其他 wiki 页。
- 当前进度 → `10_active/<项目>/STATUS.md`，由你唯一写入（主要依据最近 7 天的会话记录和提交）：最近 7 天的决定和改口、进行中的事和卡点、待办。每晚整体改写成「现在的状态」，不按日期堆；不超过 80 行。若某来源当晚缺失，保留上一版中来自该来源的未结事项，不凭空删掉。用户写的 `HANDOFF.md` 你只读，内容冲突时以更新且有证据的为准，并在报告里指出。

## 二、输入

### 来源和出处 ID

出处 ID 必须能让人按 ID 找回原文。只用下表里的前缀。遇到表里没有的来源，不要自己发明前缀：在运行报告里提出，由用户加到这张表。

| 前缀 | 来源 | 原文在哪 | 例子 |
|---|---|---|---|
| `codex:` | Codex 会话 | `%USERPROFILE%\.codex\sessions\` | `codex:<会话ID>#<序号>` |
| `claude:` | Claude Code 会话 | `%USERPROFILE%\.claude\projects\*\<会话ID>.jsonl` | `claude:<会话ID>#<序号>` |
| `agy:` | Antigravity 桌面端对话 | `%USERPROFILE%\.gemini\antigravity\brain\<会话ID>\` 下的对话记录 | `agy:<会话ID>#<行号>`（JSONL 物理行号，从 1 起） |
| `inbox:` | 日常 Agent / 用户写的待整理条目 | 本仓 `inbox/` | `inbox:2026-01-15.md#2` |
| `git:` | Git 提交 | 本仓或对应仓库 | 本仓 `git:<短号>`，其他仓库 `git:<仓名>@<短号>` |

### 每条记录要读什么

- 用户原话、助手最终结论、**以及支撑结论的证据**：命令和退出码、测试结果、提交号、截图说明、用户的明确验收。
- **派活会话**：Codex 会话元数据里 `originator` 为 `codex_exec` 或 `source` 为 `exec` / `subagent` 的会话、`agy-ask` 的 CLI 顾问会话、各工具的子代理会话。采集时与交互会话分开计数；其中的 `user` 消息是派活提示词，不计为用户消息，不取材。
- 派活会话只取回执和工具输出里的实测证据（命令、退出码、测试结果、踩坑根因、对照实验），不取执行者的建议、待定事项或草稿，也不得用作用户决定或偏好的出处。
- 排错过程里「试了什么、为什么不行」要保留到能写出陷阱的程度。不要只留用户原话——那会丢掉最有用的部分。
- 普通闲聊、一次性查询、可以直接从屏幕或代码里读到的状态，不记。
- 不采集你自己（夜间整理）的会话。

### 缺了什么要说出来

运行开始先列出每个来源这次的状态：`已采集 N 条` / `源存在但未采集` / `源不存在` / `用户暂停`。
「源存在但未采集」和「源不存在」必须分开写。主力来源是 Codex 和 Claude Code：其中任何一路这晚不是「已采集」或「用户暂停」，都在运行报告**开头**醒目提醒。

**来源不全时不做按时间的删除**：只要主力来源有一路没采集到，本晚跳过「30 天移待核、60 天删除」，因为「没再提到」可能只是没采集到。

### 用户的手动改动优先

用下面的命令找出你上次提交之后、不是你提交的改动：

```bash
last=$(git log -1 --author='^dreaming-bot' --format=%H)
git log "$last..HEAD" --perl-regexp --author='^(?!dreaming-bot).*$' --format='%h %an %s' -- 20_wiki MEMORY.md
```

这些提交视为用户纠正，吸收进页面，不要改回去。出处优先级：`git:` 提交 > 用户原话（交互会话）> `inbox:`。命令出错时，退回看最近 3 天的全部提交，并在报告里写明。

## 三、摄入：怎么写 wiki

- **按主题组织，不按日期。** 不要写 `## 2026-01-15 · …` 这种小节。新内容并进已有主题小节；没有合适主题才新开小节或新页。
- 相同事实只在一页写全，其他页用链接 `→ 20_wiki/xxx.md#小节` 指过去。
- 每条必填出处 ID 和状态（`已核` 有证据，`未核` 只有助手或用户自述）。规则、核实方法、最后核实日期和陷阱按内容需要选用。
- `未核` 条目可以进 wiki，但 30 天内没被核实或再次提到，回头整理时移到页面末尾「待核」小节；60 天仍无下文，删掉（git 里有历史）。
- 进行中的事（选型、某次排障、还没拍板的方案）属于 `10_active/<项目>/`，不进 wiki；等有结论再进。

## 四、回头整理

按变化和风险挑选，优先看今晚摄入碰到的矛盾或重复页、会改变决策的条目、准备提升到 `MEMORY.md` 的条目。整理多少由你判断，报告里写挑了什么、为什么。没有新材料且无矛盾的晚上，可跳过回头整理，只报来源状态。`MEMORY.md` 每周日照常检查。

- **核对**：按出处找回原文，看选中的条目是否写对了。写错的改正，并在运行报告里列出。
- **合并**：同一件事分散在多处的，合成一条；按日期堆的小节改成按主题。
- **清过时**：被后来的决定推翻的、已完成的待办、和别处矛盾的，删掉或改写。拿不准哪个新，以出处时间更晚且有证据的为准；都没证据，两条都留并标「矛盾待核」。
- **补链接**：页与页之间该互链的补上；`MEMORY.md` 导航与实际页面对齐。
- 整理完在 `ops/state/review.md` 更新该页的「最后整理」日期。

除 `STATUS.md` 外不要动 `10_active/` 里的文件；发现里面有和 wiki 矛盾的内容，写进运行报告的「请用户处理」。

## 五、体量

- `MEMORY.md` ≤ 80 行；滚动区 ≤ 5 条，只放会影响以后决定的已落地变化。
- 单页 wiki 超过 150 行或约 10 KB 时考虑拆页或瘦身；`STATUS.md` 控制在约 4 KB 内。
- 每条只留最关键的 2～3 个出处 ID。
- 单页不应比它引用的原料还长。页面在变长而条目在重复，说明没在抽象，优先回头整理。
- 去重账本放 `ops/state/digested.md`（旧笔记）和 `ops/state/inbox-done.md`（inbox），不放 `20_wiki/`。

## 六、提交和安全护栏

1. 开始前 `git pull --rebase`。如果 pull 本身就冲突：`git rebase --abort`，本晚只写运行报告、不改任何页面，报告开头写明冲突的文件。
2. **有没合并的 `dream/*` 分支时**（`git ls-remote --heads origin 'dream/*'` 有结果），本晚只摄入、不删不改写旧正文，并在报告开头提醒用户先处理那个分支。
3. **按两步暂存和提交**，开始前确认暂存区为空，**不要 `git add -A`**。
   - 先逐个处理 `10_active/<项目>/STATUS.md`：每个项目只暂存该文件，单独提交 `dream: <日期> STATUS <项目>`，直接推 main。
   - 再暂存其余负责路径（`20_wiki/ MEMORY.md ops/state/`），运行 `git diff --cached --numstat`，按第 5 条决定在哪个分支提交。
4. 其余改动的提交信息为 `dream: <日期> 摄入 N 条，整理 <页名…>`，正文写删除和改正了哪些条目。
5. **大改动不直推 main**：按暂存区的 `numstat` 输出计数（不要自己估）。任何一个文件删掉的行数达到原行数的 30% 或 5 行以上，或全部文件合计删除超过 30 行，先 `git checkout -b dream/<日期>`，再提交并推送该分支，最后 `git checkout main`，报告里请用户审。未达到门槛就在 main 提交并推送。从 `ops/state/runs/` 删掉的过期报告不计入删除门槛。
6. push main 遇到冲突：不 force-push。把当前提交推到远端 `dream/<日期>`（`git push origin HEAD:refs/heads/dream/<日期>`），报告里写明。
7. 凭据目录（含 `secrets/`）只登记路径，不读正文；不写明文凭据。
8. **提交前扫密钥**：`git config core.hooksPath ops/hooks` 已启用时，每次 `git commit` 会自动跑 `ops/hooks/pre-commit`。被拦时只删掉或换成 `[REDACTED]` 那几行，绝不加 `--no-verify` 跳过；报告里写命中的文件和处数，不写内容。原始会话里可能有用户贴过的明文 Key，摘录原话时同样不能带进页面。

## 七、运行报告

写到 `ops/state/runs/<日期>.md`（只保留最近 14 份，更早的删掉）。三项必写：

- **来源状态**：按第二节逐个列出来源、状态和条数，交互会话与派活会话的采集数分列。
- **实质纠错**：列出改正的条目和出处。没有就写「无」。
- **请用户处理**：列出待核矛盾、`10_active/` 里的问题、连续缺失的来源、推到 `dream/` 分支的改动等。没有就写「无」。

其余从简。做了回头整理就写挑了什么、为什么。
